# 밀리버릿 (Mealiverit) — Infra

> 대규모 트래픽 선착순 쿠폰 발급 시스템의 인프라 레포지토리입니다.
> 담당: 윤태형 (인프라/부하테스트) · 팀 태진아
> 상위 기획/설계 문서: `01_기획서.md`, `02_아키텍처.md`, `03_시스템설계.md`, `04_기술문서.md`

이 레포는 애플리케이션 코드가 아니라, 애플리케이션이 돌아가는 **로컬 개발 인프라(Docker Compose)**와 **부하테스트(k6)** 를 담당합니다. "재고 10,000장 vs 동시요청 20,000명 상황에서 초과발급 0건"을 검증하는 것이 이 프로젝트의 핵심 목표이기 때문에, 인프라 구성도 그 목표(정확성 검증)에 맞춰져 있습니다. 처리량/속도 자체는 평가 대상이 아니므로, 최적화보다 **정확한 재현 가능성**을 최우선으로 설계했습니다.

## 1. 전체 구성 한눈에 보기

```
[개발자 로컬 PC]
 ├─ docker-compose.yml
 │   ├─ mysql   (로컬 개발/테스트용, Testcontainers 대체 가능)
 │   ├─ redis   (동시성 제어 게이트 — V2.1 이중 카운터)
 │   └─ kafka   (선택, Phase 4에서만 기동)
 │
 ├─ Spring Boot 앱 (별도 레포)
 │   └─ application.properties → 환경변수로 DB/Redis 접속정보 주입
 │
 └─ k6 부하테스트 (src/test/loadtest/)
     └─ 네트워크로 API 서버에 접근 가능한 어떤 머신에서도 실행 가능

[원격 호스트] 100.125.247.64:3306 (Tailscale VPN 경유)
 └─ MySQL — 실제 팀 공용 DB (100만 User / 300만 CouponIssue 등 더미데이터 적재 대상)
```

**왜 로컬 Docker Compose에도 MySQL이 있는데, 원격 DB(Tailscale)도 따로 쓰는가?**
- 로컬 `mysql` 컨테이너는 각자 PC에서 스키마/쿼리/배치를 빠르게 실험하고 깨뜨려도 되는 **개인 개발용 샌드박스**입니다.
- 원격 호스트(`100.125.247.64:3306`)는 팀 전체가 공유하는 **단일 정본(source of truth) DB**로, 100만 User·300만 CouponIssue 더미데이터가 실제로 적재되는 곳입니다. 6명이 각자 로컬 DB를 따로 쓰면 "내 컴퓨터에서만 재현되는 버그", "누구 데이터가 최신인지 모름" 같은 문제가 생기기 때문에, 정합성 검증(300만 건 대상, 결정론적 재실행)처럼 팀 전체가 같은 결과를 봐야 하는 작업은 반드시 원격 DB 기준으로 수행합니다.
- 연결은 각자 공개 인터넷에 포트를 열지 않고 **Tailscale(WireGuard 기반 메시 VPN)**으로 사설망처럼 접속합니다. 방화벽/포트포워딩 설정 부담 없이 팀원 6명의 로컬 PC와 원격 호스트를 하나의 프라이빗 네트워크로 묶기 위해 선택했습니다.

## 2. 왜 이 인프라 구성을 선택했는가

### 2.1 Docker Compose (전체 오케스트레이션 도구)
- **선정 이유**: 회원가입/로그인이 없는 프로젝트 특성상 인프라도 "가볍게, 빨리 띄우고 내리는" 것이 중요합니다. Kubernetes 같은 무거운 오케스트레이션은 이 과제 규모(팀 프로젝트, 로컬 개발)에 과도하고, 개인 개발환경 통일이 목적이므로 `docker-compose.yml` 하나로 MySQL/Redis/Kafka를 명령어 한 줄(`docker compose up -d`)로 재현 가능하게 만드는 것을 우선했습니다.
- **담당 기능**: 로컬 개발용 MySQL·Redis·(선택) Kafka 컨테이너의 정의, 포트 매핑, 볼륨 마운트, 헬스체크, 팀원 간 동일한 개발 환경 보장.

### 2.2 MySQL (로컬 컨테이너 + 원격 Tailscale 호스트)
- **선정 이유**: 팀이 이미 확정한 DB. 정합성 검증이 SQL 집계 쿼리로 이뤄지는 프로젝트 특성상(`03_시스템설계.md` 1절), RDBMS의 강력한 제약조건(UNIQUE, 트랜잭션)이 "초과발급 0건, 1인 1매"를 물리적으로 보장하는 최후 방어선 역할을 합니다.
- **담당 기능**:
  - `uk_campaign_user` (campaign_id, user_id) UNIQUE — 1인 1매 최종 방어선
  - `uk_idempotency_key` UNIQUE — 중복 요청 방지
  - 100만 User, 300만 CouponIssue, orders(약 1,000만 건) 등 더미데이터의 실제 저장소
  - 정합성 검증 SQL 6종(재고 초과 여부/중복 발급/카운터-이력 불일치/상태전이 위반/등급 위반/계급 정합성)의 실행 대상
- **로컬 vs 원격 역할 분리**: 로컬 컨테이너는 개인 개발·단위 테스트용, 원격 Tailscale 호스트(`100.125.247.64:3306`)는 팀 공용 정본 데이터.

### 2.3 Redis
- **선정 이유**: MVP(V1.0)는 DB 비관적 락만으로 정확성을 증명하지만, hot row 경합으로 처리량이 떨어지는 문제가 실측되면서(`02_아키텍처.md` 4절) 하드닝 단계에서 Redis 기반 원자적 카운터 게이트가 필요해졌습니다. 여러 전략(Lua 스크립트, Redisson 분산락, 이중 카운터)을 비교한 뒤, 국내(올리브영) 실측 데이터를 근거로 **이중 카운터(V2.1)** 방식을 최종 채택했습니다 — Lua 대비 오버헤드가 낮고(올리브영 실측 Lua -21% vs 이중카운터 -8%), 구현 복잡도도 Redisson/Kafka 조합보다 낮습니다.
- **담당 기능**:
  - `countReq`(1차 저비용 필터) / `count`(2차 확정, 실패 시 자체 롤백) 이중 카운터로 재고 차감의 원자성 보장
  - DB 커넥션 풀 고갈·락 대기 타임아웃 문제를 우회하는 1차 게이트키퍼
  - 선택 확장: `stock:{campaignId}:remaining` 키를 SSE/WebSocket으로 push하는 실시간 재고 카운트다운 대시보드의 데이터 소스
- **중요한 운영 원칙**: Redis는 반드시 **마스터 단일노드**로만 구성합니다. 배민 빼빼로데이(2016) 사례에서 복제 노드 참조로 실제 초과발급(1,111명)이 발생한 반례가 있어, Compose 설정에서 복제본을 두지 않는 것이 원칙입니다.

### 2.4 Kafka (선택, Phase 4)
- **선정 이유**: 기본 아키텍처(V1.0→V2.1)는 Kafka 없이도 요구사항을 충족하므로, 기본 구성에서는 제외했습니다. 다만 (d) Redis+MQ 비동기 분리 전략을 시간 여유가 있을 때 PoC로 검토하기로 팀이 합의했기 때문에 Compose에 선택적으로 포함해 둡니다.
- **담당 기능(도입 시)**: 발급 요청의 트래픽 스파이크를 큐로 흡수, Consumer 멱등성/DLQ 기반 비동기 처리. 다만 eventual consistency가 발생해 "즉시 정합성 검증"이라는 이 프로젝트의 핵심 평가 포인트와 설명 부담이 커, 기본값은 **비활성 상태**로 유지합니다.
- **로컬 자원 이슈**: MySQL+Redis+Kafka를 동시에 띄우면 로컬 자원이 부족해질 수 있어, 기본 개발 환경은 MySQL+Redis만 기동하고 Kafka는 필요할 때만 별도 프로필로 올립니다.

### 2.5 Tailscale (원격 DB 접속)
- **선정 이유**: 팀원 6명이 하나의 공용 DB(`100.125.247.64:3306`)에 접속해야 하는데, 공개 인터넷에 MySQL 포트를 직접 열면 보안 위험이 크고, VPN 서버를 직접 운영/관리하는 것도 이 프로젝트 범위를 벗어나는 오버엔지니어링입니다. Tailscale은 WireGuard 기반으로 설정 없이 팀원들의 디바이스를 하나의 사설망처럼 묶어주기 때문에 채택했습니다.
- **담당 기능**: 팀원 로컬 PC ↔ 원격 MySQL 호스트 간 암호화된 프라이빗 네트워크 연결. 애플리케이션은 이 네트워크를 통해 일반 사설 IP처럼 `100.125.247.64:3306`에 접속합니다.

### 2.6 k6 (부하테스트)
- **선정 이유**: 과제 원문(`00_과제원문.md`)에서 부하테스트 도구는 자유(JMeter, k6, 자작 클라이언트 등)이며 도구/처리량 자체는 평가하지 않는다고 명시되어 있습니다. k6는 JavaScript로 시나리오를 작성할 수 있어 팀 내 러닝커브가 낮고, `shared-iterations` executor로 "정확히 20,000회 요청"처럼 결정론적인 시나리오 수를 고정하기 쉬워 이 프로젝트의 핵심 요구사항(재현 가능한 정확성 검증)에 적합했습니다.
- **담당 기능**:
  - 재고 10,000 vs 동시요청 20,000(서로 다른 유저) 메인 시나리오
  - 동일 유저 다회 재요청(예: 5,000명 × 4회) 1인 1매 서브 시나리오
  - 스크립트 위치: `src/test/loadtest/` (네트워크로 API 서버에 접근 가능한 어떤 머신에서도 실행 가능)
  - 테스트 종료 후에는 k6 자체 지표가 아니라 DB 쿼리(`SELECT COUNT(*) FROM coupon_issue ...`)로 최종 판정 — k6는 트래픽 재현 도구일 뿐, 정확성 판정은 항상 DB가 기준입니다.
  - 동일 시나리오를 5회 이상 반복 실행해 매번 초과발급 0건이 재현되는지 확인하는 것이 목표입니다.

## 3. 실행 방법

```bash
# 1. 로컬 인프라(MySQL, Redis) 기동
docker compose up -d

# 2. (선택) Kafka까지 포함해서 기동 — Phase 4 PoC 시에만
docker compose --profile kafka up -d

# 3. 상태 확인
docker compose ps

# 4. 종료
docker compose down
```

k6 부하테스트 실행 예시:

```bash
BASE_URL=http://localhost:8080 k6 run src/test/loadtest/coupon_race.js
```

## 4. 환경변수

DB 자격증명은 절대 `application.properties`나 `docker-compose.yml`에 하드코딩하지 않습니다(`05_개발표준.md` 3절 보안 체크리스트). `.env` 파일(커밋 금지, `.gitignore` 등록)로 관리합니다.

| 변수 | 설명 | 예시 |
|---|---|---|
| `DB_URL` | 원격 MySQL 접속 URL (Tailscale 경유) | `jdbc:mysql://100.125.247.64:3306/mealiverit` |
| `DB_USER` | DB 사용자 | (팀 공유, 커밋 금지) |
| `DB_PASSWORD` | DB 비밀번호 | (팀 공유, 커밋 금지) |
| `REDIS_HOST` | 로컬 Redis 컨테이너 호스트 | `localhost` |
| `REDIS_PORT` | 로컬 Redis 포트 | `6379` |
| `BASE_URL` | k6가 요청을 보낼 API 서버 주소 | `http://localhost:8080` |

## 6. 알려진 리스크 및 대응 (인프라 관점)

| 리스크 | 영향 | 대응 |
|---|---|---|
| Redis를 복제 구성으로 잘못 띄우면 카운터 불일치 발생 가능 | 초과발급 재현 (배민 빼빼로데이 반례) | Compose에서 Redis는 단일 마스터 노드로만 구성, 복제본 추가 금지 |
| DB 비관적 락(전략 a) hot row 경합 시 부하테스트 중 타임아웃 다발 | 데모 중 5xx 대량 발생처럼 보임 | `innodb_lock_wait_timeout` 조정, VU 수를 단계적으로 올려 부하테스트 진행 |
| MySQL+Redis+Kafka 동시 기동 시 로컬 자원 부족 | 개발 환경 불안정 | 기본은 MySQL+Redis만 기동, Kafka는 `--profile kafka`로 필요할 때만 |
| Tailscale 미접속 상태에서 원격 DB 접근 시도 | 로컬 개발 중단 | 각자 PC에 Tailscale 클라이언트 상시 로그인, 접속 확인 후 앱 기동 |
| 원격 호스트 네트워크 지연(Tailscale VPN 경유) | HikariCP 커넥션 타임아웃 | `connection-timeout`, `validation-timeout`을 로컬 기준보다 여유 있게 설정 |
